GPU start-up and timing: why one run shows 221 ms and the other 114 ms

./tree --gpu, CART depth ≤ 10, HIGGS, H100 (hopper), commit 713914b8. Same tree, same build; the GPU setup sits on different sides of the timer.

1 · What happens in the process, to scale

Main thread and the background GPU thread, measured (A/B job 312, HIGGS read from memory, medians of 10). The stopwatch ("timed training") covers only the black bracket.

process start, exit, other read data CUDA context kernels (all, eager) + memory pool + staging buffers + copy threads main thread waits for the GPU thread GPU setup: upload, presort, allocations …+ pool, staging buffers, kernels on first use build

Both measured in the same job, interleaved, 16 threads on one socket (the end-to-end chart uses 32, hence 221 / 114 ms there vs 183 / 106 ms here). "Other" (process start, exit) is drawn as one block at the start. The split of full's start-up into context + rest assumes the context takes the same 529 ms as in context mode. Short read: both modes finish at the same time.

MNIST8M (25 GB) read from NFS: a read much longer than the start-up

./tree --gpu, CART depth ≤ 10, ampere (A100 80 GB, 24 threads on the GPU's socket), job 326, medians of 3 per mode. The read is broken (zigzag); everything else to scale.

The start-up (0.45–0.59 s) ends long inside the read, so neither mode waits. full's extra start-up work is hidden; context does it in the timed setup instead: 3,105 vs 3,223 ms timed, ~120 ms (GPU setup 1,225 vs 1,345 ms; build 1,880 ms in both). The read is drawn the same for both: 20.6 s (median of context's runs); full's runs read in 30.3, 26.1 and 21.7 s, NFS varying between runs (the coldest run came first), not the mode. Process start and exit ~0.3 s.

2 · Which work is inside the timer

Every GPU tool does the same kinds of work. The question is where each piece lands.

before the timer (not timed) before the timer, hidden behind the read timed

cuML and XGBoost cannot load their kernels or set up their memory pools outside their own fit without running it (a warm-up), so for them all of it is timed. context gives ./tree the same rule.

3 · The work did not shrink, it moved

Total GPU preparation = start-up + timed setup, measured side by side (HIGGS from memory, medians). About the same total; full does it earlier, off the stopwatch.

--gpu: 645 vs 647 ms, the same work. --hybrid: 781 vs 837 ms, but --hybrid on hopper is noisy (p10–p90 of its runs spans ~600 ms). An earlier estimate of "~100 ms more for full" compared different runs and did not hold up.

4 · What each way of timing would report against the libraries

Same runs, three possible rules. Bars: ./tree --gpu vs cuML and XGBoost (1 tree), CART, HIGGS, H100.

Library times: their fit (cuML) / QuantileDMatrix + train (XGBoost) and CUDA context from the end-to-end runs. Rule C: everything after the data is in memory, GPU start-up included (./tree: the part of its start-up still running after the read).

5 · How to handle it

Recommended: A, now backed by the measurement in section 6.

A · Keep the flag (now)

fairno reruntwo modes
  • Library comparison: training under one rule (context): 221 ms vs 1.38 s.
  • ./tree's overlap is credited in the end-to-end chart (full), where wall time counts.
  • End-to-end chart's "timed" bar should show 221 ms for ./tree GPU rows.
  • Measured (section 6): full is the faster default, never slower.

B · Drop the flag, always full, keep the training timer

not fairrerunone mode
  • ./tree's setup leaves the timer, the libraries' stays in: 114 ms vs 1.38 s.
  • The 2× gain is not faster work, only work moved out of the stopwatch.
  • A reviewer would catch it.

C · Drop the flag, always full, time from data in memory

fairone modefull GPU rerun
  • Every tool's CUDA context and setup counted; ./tree's overlap credited for real.
  • ~0.7 s of CUDA context for everyone: 0.90 s vs 2.08 s; algorithm differences shrink.
  • Reruns cluster-higgs, cluster-susy, gpu-vs-others on hopper and ampere.

6 · Measured: does full make the whole run faster?

A/B on hopper, job 312: 3 modes × 2 backends × 10 interleaved runs per case, CART depth ≤ 10, one socket (16 threads) and one H100 per stream. Bars: read + GPU wait + training (median), whiskers p10–p90.

context full (default, eager kernels) full with lazy kernels

Process start and exit (~160–440 ms, the same for every mode) are left out: they vary by up to 600 ms between runs and would hide the differences. Every run built the same tree (2,029 / 2,047 nodes). MNIST8M: the GPU start-up always finishes inside the 1.5 s read, so neither mode waits; its setup (~700 ms) is mostly the 25 GB upload, which no start-up mode can move.

Answer: full never loses and wins ~130–200 ms when the read takes longer than the start-up (HIGGS from NFS: read 955 ms). With a short read (HIGGS from memory, 76 ms) all three modes finish within noise of each other: eager kernel loading costs about what it saves. Lazy kernels in full gave no clear gain. Keep full as ./tree's default; use context only where ./tree is timed against libraries.
